# Coverage: PM Calendar (v2, `screens/v2/pm-calendar/`)

Built from `screens/analytics/PmCalendar.tsx`, `PmCalendarPage.tsx`, `pm-calendar-parts.tsx`, `pm-calendar-move.tsx`, `pm-move.ts`,
`pm-calendar-view.ts`, their tests, `e2e/pm-calendar.spec.ts`, SPEC.md (PM calendar, M4b: checklists and load spreading) and the routes
`GET /pm/calendar`, `POST /pm/reschedule` (`apps/server/src/modules/tickets/pm-routes.ts`) plus the `pm-compliance` figure. PARITY.md has no row for it.

**Live (ticket 91).** The screen is at `/analytics/pm` (v1's address; any `?screen=` opens it) and reads what v1 read: `GET /pm/calendar` under v1's own query
key (`pmCalendarQuery`, shared cache), the `pm-compliance` figure from `GET /analytics/figures` and the signed-in role (`live.ts`); the write is v1's `POST /pm/reschedule`
(`schedulePm`) through `createMover`, one idempotency key per attempt, the server's refusal in its own words. After a landed move the calendar, the tickets and the figures are
read again, as in v1; the figures' 30-second refresh also marks the calendar old and reads it again (`refreshCalendar`). A job is keyed by its machine's code (the engine
gives one occurrence per machine), so a drag or a button is paired with its own row by that code and never by position, and no database id is printed or keyed on.
`plans.json` and `stand-in.ts` are the **gallery and test providers only** (the seam's `frozen` entry): derived from the real workbook by the seed's own mapper and held
equal to it by a test, never read by the live screen. v1's page (`PmCalendarPage.tsx`, `PmCalendar.tsx`, `pm-calendar-parts.tsx`, `pm-calendar-move.tsx`, `pm-move.ts`,
`pm-calendar.css`, their unit tests and the lazy route) is deleted in the same PR; the FullCalendar chunk guard now names the v2 door alone. v1's assertions live on in
`keyboard-move.test.ts`, `refused.test.ts`, `live.test.ts`, `pm-calendar-view.test.ts` (what the machine page still uses) and the real-server `pm-calendar.spec.ts`.

**Data.** `adapter.ts` takes the calendar reply (`PmCalendarReply`), the `pm-compliance` figure value and whether the login is head or admin. The
gallery reply is the engine's, not invented: `plans.json` is what the seed's own `mapPmPlans` makes of the 11 November workbook (125 plans; a
test holds it equal), and the calendar is the domain's `pmCalendar` run over them, so crowding and the nearest free day are the engine's.
The workbook holds no PM work orders, so the compliance figure is the engine's hand-worked fixture (`PM_COMPLIANCE_EXPECTED`, 50b; a test
holds it equal). In the gallery the write is a stand-in that mirrors four server refusals; live, the real server decides. No server change is needed.
**Heavy library.** The calendar library is named only in `ui/v2/domain/month-calendar.tsx`, reached through `React.lazy` (ADR 0009 R1); the
chunk guard test lists both v1's door and this one.
