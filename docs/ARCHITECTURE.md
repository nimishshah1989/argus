Written 13 November 2026 from `docs/BRIEF.md` (scope, order, design rule; it wins over the spec), `docs/spec/SPEC.md` §5–§9, `docs/spec/DOMAIN.md`, `docs/plan/ROADMAP.md` §2/§3/§8 and the code on this branch. Part 1 is what exists. Parts 2–8 are the target for the remaining scope in the BRIEF's order. Part 9 is the list of changes that takes the code from one to the other.

Words used here: a **module** is a folder in `apps/server/src/modules/` with one published interface; a **package** is a pnpm workspace package under `packages/`; a **face** is one of the web app's route groups (floor, desk, board, management, settings).

"Verify in current docs" marks a library or API that is not installed in this repo yet: the slice planner checks the official documentation before a plan names a function from it. Decisions are numbered D1–D12; each is written to be filed as one file in `docs/decisions/` (the folder does not exist yet).

## 2. Target: one modular monolith

One Fastify process, one Postgres, one S3 bucket, one static web app (SPEC §5, ADR 0001, ADR 0002). Nothing in the BRIEF needs a second service, so none is added.

**Shape of a module.** `apps/server/src/modules/<name>/` holds `index.ts` (the published interface and nothing else), `routes.ts`, `service.ts`, `repo.ts` (the only file that contains SQL), `jobs.ts` and `test/`. `index.ts` exports one object `{ name, register(app), jobs, subscriptions }` plus the published functions. `apps/server/src/modules/index.ts` lists the modules; `app.ts` loops over that list. A module's routes, queues and tests never touch a shared file.

**Rules.**

1. Every table has exactly one owning module. Only the owner's `repo.ts` names that table in SQL. Foreign keys across modules are allowed (integrity is not access).
2. A module reads another module's data by calling a published function and passing the open transaction (`tx`), so the read stays inside the same tenant transaction. No cross-module joins. Names for display come from `/config` in the web (already cached) or from `identity.peopleByIds` / `plant.machinesByIds` on the server.
3. Calls follow the table below and never form a cycle. Where a lower module must react to a higher one, it publishes an **event** and the higher module subscribes at start-up. Subscribers run inside the publisher's transaction, so the ticket, its timers and its queued jobs commit or roll back together (ADR 0006 already requires this).
4. Business rules stay in `packages/domain` (SPEC §6). A module loads rows, calls the pure function, stores the result.
5. Every handler receives `{tenantId, login, actingPersonId, now}` (SPEC §6). Every command is idempotent on its key; every job handler re-reads state and is a no-op when already done.

**Kernel** (`apps/server/src/kernel/`, not a module, owns no tables): `withTenant` re-export, request context, the error envelope, the logger, the job registry (`defineJob`, `enqueue(tx, …)`), the event bus (`publish(tx, event)`), `defineModule`. Every module may import the kernel; the kernel imports no module.

**How boundaries are enforced in CI (D1).** Three mechanisms, none of which adds a dependency:

1. **Workspace wiring.** Every cross-package import is a declared `workspace:*` dependency, and each package's `package.json` `exports` map exposes only its entry points. The root `tsconfig` path aliases are removed, so an undeclared or deep import fails typecheck and build.
2. **Import rule.** ESLint core `no-restricted-imports` (ESLint is already installed) forbids relative imports that leave an app (`../../../packages/**`) and imports of another module's files other than `modules/<name>/index`.
3. **Ownership check.** A new `tools/check-boundaries.ts`, in the style of the existing `tools/check-*.ts`, reads one manifest (`apps/server/src/modules/manifest.ts`: tables owned, modules callable) and fails when SQL appears outside a `repo.ts`, when a `repo.ts` names a table its module does not own, or when a module imports one it may not call. It runs in `pnpm verify`.

Rejected: `eslint-plugin-boundaries` and `dependency-cruiser` (both would need "verify in current docs" and an ADR under `docs/LEAN.md`; neither checks table ownership, which is the rule that matters here); separate packages per module (thirteen more `package.json` files for no extra safety).

## 3. Data access (D2)

**Decision: keep raw SQL on `pg`. Do not adopt Drizzle.** ADR 0001, SPEC §5/§6 and `THIRD_PARTY.md` are corrected to say so.

| Reason                            | Detail                                                                                                                                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| It is what runs                   | 163 queries, 507 tests on real Postgres, the generic isolation test, the ledgered SQL migrations. A rewrite before cutover adds risk and changes nothing a user sees (BRIEF order: cutover first) |
| The hard parts are SQL either way | RLS policies, `SECURITY DEFINER` functions, `FOR UPDATE` locks, partial indexes, and pg-boss writes on the ticket's own client (ADR 0006) are raw SQL in any stack                                |
| Lean                              | No new dependency (`docs/LEAN.md`)                                                                                                                                                                |

What raw SQL costs, and the answer: no compile-time check that a query matches the schema. So (a) SQL lives only in `repo.ts`; (b) each `repo.ts` maps rows to the shared Zod type at its edge, and the route replies through that schema; (c) every repo function has a test on real Postgres, as today.

Rejected: **Drizzle** (retrofit of 163 queries; two query styles during the move; its schema file would be a second source of truth beside the SQL migrations); **Kysely** or a SQL-to-types generator (a new dependency for a problem the repo tests already catch). **Revisit trigger:** two production defects caused by a query and schema disagreeing, or the M4a engine result queries needing dynamic SQL that string-building makes unsafe.

## 4. Contracts (D3)

- **One source of truth:** Zod schemas in `packages/shared`, one file per module (`shared/src/tickets.ts`, `plant.ts`, …), exposed as subpath exports (`@uptimo/shared/tickets`). The `index.ts` barrel is removed. Each schema file exports the schemas and their inferred types and nothing else.
- **Server:** every route validates the request and builds the reply with the shared schema. The spec names Fastify's Zod type-provider; it is not installed, so the planner either adds it with an ADR (verify in current docs) or keeps the existing `safeParse` pattern behind one `route()` helper in the kernel. Default: the helper.
- **Web:** types come from `z.infer` of the same schemas through the `@uptimo/shared` workspace dependency. `apps/web/src/api-types.ts` and the duplicate DTOs in `packages/domain/src/types.ts` are deleted; `domain` keeps only its own internal types.
- **Versioning:** the API is `/api/v1`. Within v1 a change is additive only (new optional fields, new endpoints); a breaking change is a new path under `/api/v2` with the v1 route kept for one release, because phones run a cached build (SPEC §6 expand-and-contract applies to contracts as well as tables). Job payloads and events carry `v: 1` and are parsed by a shared schema.
- **Errors, pagination, idempotency:** as SPEC §8.7; one envelope, one cursor shape, one `Idempotency-Key` header, implemented once in the kernel.

**Settings screens are generated (D5).** A settings screen is one file `faces/settings/resources/<name>.ts` exporting a `ResourceSpec`: `{ key, path, schema, columns, fields, permission, titleKey }`. `schema` is the shared Zod schema; `columns` and `fields` are typed as keys of that schema, so a renamed field fails typecheck. `CrudPage` renders the table (TanStack Table, SPEC §5a; verify in current docs), search, the add and edit sheet, validation from the schema (react-hook-form with its Zod resolver, SPEC §5a; verify in current docs), disable instead of delete, and the "what changed" audit line. The field control defaults from the Zod type (text, number, switch, select for an enum, date) and can be overridden per field (for example a person picker). Settings routes are collected from the `resources/` folder, so a new settings screen adds one file and edits none. A test fails when a schema key is neither a field nor listed as hidden. Rejected: AutoForm (SPEC §5a names it; a second form abstraction beside `FormSheet`); hand-written screens (today's four settings files total 959 lines for criticality, the severity matrix, SLA and wait-reason flags).

**Data layer (D6).** `defineResource({ key, path, schema })` returns `useList`, `useOne`, `useCreate`, `useUpdate`, `useDisable` built on TanStack Query (installed), typed from the shared schema, with the query keys and invalidation in one place. `useCommand(action)` sends a ticket command with its idempotency key, applies the optimistic update for that ticket only (SPEC §7) and hands the four offline-allowed commands to the outbox. `/state` and `/config` keep the 30-second refetch and fingerprint (SPEC §7). Responses are parsed with the shared schema; if the 1.19 performance measurement shows the `/state` parse matters on a low-end phone, that one endpoint switches to type-only.

**Rules shared with the server.** The action bar calls `availableActions(ticket, actor)` from `packages/domain`; `apps/web/src/components/actions.ts` is deleted. The server calls the same function before it applies a command, so the button a person sees and the permission the server enforces cannot disagree.

**i18n (D7).** Message catalogues move to `packages/shared/src/i18n/<namespace>.en.ts` and `<namespace>.gu.ts` (SPEC §9: all strings in `packages/shared/i18n`; the server needs them for push text and PDFs). Namespaces: `common`, `status`, `actions`, `errors`, `floor`, `desk`, `board`, `settings`, `analytics`, `pm`, `ai`, `notify`, `pdf`. Each file stays under 250 lines. Two guards: the existing `i18next/no-literal-string` rule for `.tsx`, and for `.ts` a type: every label field in an action, status, column or field spec is typed `MessageKey` (the union of catalogue keys), so an English literal fails typecheck. Gujarati entered by Cosmos on the translation screen is stored per tenant in `ui_translation` and laid over the bundled catalogue at load; untranslated keys fall back to English and appear on the admin's list (SPEC §7). Nothing is machine-translated.

**Offline (D8).** Keep what is built: the IndexedDB outbox, replay on app open and on reconnect, 409 becomes a draft. No Background Sync (Chromium-only, SPEC §5a), so the service worker never needs the token and the token stays in `localStorage`; this departs from SPEC §7's wording and is recorded. Added: one `SyncState` entry in the status vocabulary (online, offline, sending, needs attention) rendered by one banner, and the update banner with the shift-changeover hold (ROADMAP 1.16).

**Charts.** One hook `useChart(spec)` and one `<Chart>` in `ui/`, ECharts loaded lazily (SPEC §5a; verify in current docs), palette read from the tokens. No file outside `ui/chart/` imports the chart library.

**Component gallery (D9).** A route `/gallery` inside the app, shown on local and staging only, renders every token, kit component, status and page pattern with fake data in English and Gujarati at 360 px. This is the "live component gallery" Nimish approves (BRIEF). Rejected: Storybook or Ladle (a new toolchain and a second deploy for one reader).

## 6. Jobs, notifications, engine, AI

**Jobs and timers.** pg-boss stays the only queue (ADR 0006). Each module declares its queues in `jobs.ts` with `defineJob(name, payloadSchema, handler)`; the kernel registers them. Rules carried from ADR 0006 and applied to every job: enqueue on the caller's transaction; a singleton key per subject; the handler re-reads inside `withTenant` and is a guarded no-op when the work is done or stale; a daily consistency job re-arms what should exist. Failed jobs surface on the `ops` failed-jobs page; the timer-lag alarm compares `sla_timer.due_at` with the fire time (M2-2.5).

**Notification service (M2-2.3d).** `notify(tx, {to, template, data, dedupeKey})` writes one `notification` row per recipient and channel and enqueues `notify.send` in the same transaction. A channel is an adapter:

```
ChannelAdapter { name; canReach(person); send(message) → { ok } | { retry } | { fail, reason } }
```

`push` is the only adapter until M3 (BRIEF §9). `whatsapp` and `email` register themselves from the `whatsapp` module at M3; no caller changes. The service owns retries with backoff, the dedupe key (unique per tenant), the per-channel monthly cap with fallback to push (SPEC §9), and moves a message to `notification_dead_letter` after the last attempt. Templates are message keys in the `notify` catalogue, rendered in the recipient's language.

**Analytics engine.** `packages/engine` is pure TypeScript with no I/O: `run(profile, input) → results`. The `legacy` profile reproduces Bhavin's platform exactly at a frozen as-of date; its Cosmos constants are a fixture, not product code (SPEC §11 4.2). The `standard` profile holds improved definitions (shift-calendar KPIs, M4b) and never replaces a legacy number silently (BRIEF non-negotiables). The `analytics` module loads history (`history_breakdown` plus `tickets.readHistory`), runs the engine nightly and on demand, and writes results; screens read result tables only. Results are stored narrow: `engine_run` (profile, as-of, input fingerprint) and `kpi_snapshot` (run, metric key, scope, period, value), not a table per screen, so a new figure needs no migration. `forecast` is frozen on the 1st and never rewritten; `forecast_outcome` records what happened.

**Python sidecar (D10): deferred.** The ~250 lines of statistics SPEC §5a lists (Weibull, Kaplan-Meier, Crow-AMSAA, Poisson regression) are written in TypeScript. No container is added. Trigger: an accepted ticket needs a model that cannot be written and tested in TypeScript within one slice (Bayesian or change-point models are the likely cases). Then it arrives behind the engine's own interface with its own ADR.

**AI layer (M6).** AI suggests; a person confirms; AI never produces a number or a code that is not already in the database (BRIEF §8).

| Part               | Design                                                                                                                                                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Provider adapter   | `AiProvider { complete({ task, input, outputSchema }) → { output, usage, modelRef } }`, plus `embed` only if retrieval needs it. The model is configuration, never a constant in code. A fake provider serves tests                                                                        |
| Grounding          | A suggested failure code is validated against the tenant's `failure_code` ids and dropped if absent. A plain-language analytics answer carries `kpi_snapshot` ids; the screen prints the numbers from those rows, not from the model's text. The fix finder returns ticket ids as evidence |
| Retrieval          | Postgres first: full-text and trigram search over past tickets and manual chunks, which also serves transliterated Gujarati search (SPEC §12). A vector index is added only if the evaluation harness shows text search misses the threshold (verify the extension on RDS in current docs) |
| Storage            | `ai_suggestion`: feature, subject, input fingerprint, output, evidence, model reference, prompt version, mode (shadow or live), status (pending, accepted, edited, rejected, expired), who confirmed and when                                                                              |
| Confirm            | `ai.confirm` calls the owning module's normal command (for example `tickets.applyCommand` with the failure coding, marked `suggested_by: ai`). The AI module never writes another module's table                                                                                           |
| Shadow mode        | In shadow the suggestion is stored and not shown; when the person makes their own choice, `ai_feedback` records agreement. A feature turns live per tenant by a setting, only after its threshold is met on the evaluation set and in shadow                                               |
| Evaluation harness | Built first (BRIEF §8). `ai_eval_set` and `ai_eval_case` hold labelled cases; `ai.eval` runs a provider and prompt version over a set and writes `ai_eval_run` with the metrics. CI runs the harness against the fake provider; a real run is a recorded manual job                        |
| Manuals            | `document` (the file) and `document_chunk` (text passages with page references), tenant-scoped (SPEC risks: OEM manuals stay tenant-scoped). PM drafts go to `pm.createDraftPlan` and wait for a person                                                                                    |

**Data residency for AI: open (not decided here; BRIEF open question 3, ADR 0002 requires its own decision record).** The architecture keeps all three options possible by putting one redaction step (names, phone numbers, free-text person references) in the adapter:

| Option                                         | What it means                                       | Cost and risk                                                                                             |
| ---------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| A. India-region hosted inference               | A managed model service running in an Indian region | Fits "data stays in India" as written; availability and model choice must be verified at M6               |
| B. Self-hosted open-weight model in ap-south-1 | We run the model                                    | Full control; a GPU instance far above the current ₹30,000 monthly rail; ops burden                       |
| C. Inference outside India                     | Any provider                                        | Needs the ADR and data-protection note the BRIEF demands, tenant consent (N14), and redaction before send |

No vendor or model id is chosen. Nimish answers whether plant data may leave India for AI; the technical choice among providers follows from that and from the evaluation harness.
