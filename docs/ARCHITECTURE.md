## 2. Target: one modular monolith

One Fastify process, one Postgres, one S3 bucket, one static web app (SPEC §5, ADR 0001, ADR 0002). Nothing in the BRIEF needs a second service, so none is added.

**Shape of a module.** `apps/server/src/modules/<name>/` holds `index.ts` (the published interface and nothing else), `routes.ts`, `service.ts`, `repo.ts` (the only file with SQL), `jobs.ts`, `test/`. `index.ts` calls `defineModule({ name, register, jobs, subscriptions, replyParts })`. `modules/index.ts` lists the modules; `app.ts` loops over it.

**Rules**

1. Every table and every column has one owning module. Only the owner's `repo.ts` names that table in SQL. Foreign keys across modules are allowed (integrity is not access).
2. A module reads another's data through a published function, passing the open transaction (`tx`). No cross-module joins.
3. Calls follow the table below and never form a cycle. A lower module that a higher one must react to publishes an **event** (writes) or accepts **reply parts** (reads); the higher module registers at start-up (D11).
4. A subscriber runs inside the publisher's transaction and may only write its own tables and enqueue jobs. It never calls S3, a push service, WhatsApp, speech or an AI provider in the transaction; that work is a job. A subscriber that throws rolls the command back, so subscribers do bounded, local work only.
5. Business rules stay in `packages/domain` (SPEC §6). A module loads rows, calls the pure function, stores the result.
6. Every route requires a session unless it is on the kernel's public allowlist: `GET /health`, `GET /brand`, `POST /auth/login`, `GET/POST /whatsapp/webhook` (signature-checked, M3). A new public route is an architecture change.
7. Every handler receives `{tenantId, login, actingPersonId, now}`. Every job handler re-reads state and is a guarded no-op when the work is done or stale (ADR 0006).

**Kernel** (`apps/server/src/kernel/`, owns no tenant tables, imports no module; it owns pg-boss's own tables, reached only through the pg-boss API and published as `jobs.listFailed()`, `jobs.retry(id)`, `jobs.lag()`): `withTenant`, request context, the auth guard and public allowlist, the error envelope, `route()` (parse with the shared schema, reply through it), cursor pagination, the `Idempotency-Key` header parser (storage belongs to the module, see `tickets`), `defineModule`, `defineJob`, `publish(tx, event)`, `replyParts(kind, tx, ids)`, the logger, `withTimeout`.

**Reply parts (D11).** A ticket reply carries data owned by higher modules (clocks today; handback, AI suggestions later). `tickets` asks `kernel.replyParts('ticket', tx, ticketIds)`; each registered module returns a map from ticket id to its fragment, merged under its own optional key (`sla`, `handback`, `ai`). The key's schema lives in that module's shared contract file. One query per contributor per request, never per ticket, so `/state` stays one round of reads. `tickets` imports none of them.

**How boundaries are enforced in CI (D1).** (1) Declared `workspace:*` dependencies and `exports` maps; root `tsconfig` aliases removed, so an undeclared or deep import fails the build. (2) ESLint core `no-restricted-imports` forbids imports that leave an app by relative path and imports of another module's files other than its `index`. (3) New `tools/check-boundaries.ts`, in the style of the existing `tools/check-*.ts`, reads `modules/manifest.ts` (tables owned, modules callable, dated exceptions) and fails when SQL appears outside a `repo.ts`, when a `repo.ts` names a table it does not own, or on a forbidden call. Rejected: boundary lint packages (need an ADR; none checks table ownership); a package per module.

## 3. Data access (D2)

**Keep raw SQL on `pg`; do not adopt Drizzle.** It is what runs (162 queries, 507 tests on real Postgres); RLS policies, definer functions, row locks and pg-boss writes on the ticket's client are SQL in any stack; no new dependency. Cost: no compile-time check of query against schema. Answer: SQL only in `repo.ts`; each repo maps rows to the shared Zod type at its edge; every repo function is tested on real Postgres. Rejected: Drizzle (retrofit, and a second schema source beside the SQL migrations); Kysely or a SQL type generator. Revisit after two production defects from a query and schema disagreeing, or if M4a result queries need dynamic SQL.

## 4. Contracts (D3)

- **One source:** Zod schemas in `packages/shared`, one file per module, exposed by a single wildcard subpath export (`@uptimo/shared/*`; verify the `exports` pattern in current Node docs), so adding a contract file edits neither `package.json` nor a barrel. The `index.ts` barrel is removed.
- **Server:** every route goes through the kernel's `route()`. SPEC §6 names Fastify's Zod type-provider; it is not installed, and the existing `safeParse` pattern is kept behind `route()`.
- **Web:** types are `z.infer` of the same schemas. `apps/web/src/api-types.ts` and the DTO copies in `packages/domain/src/types.ts` are deleted.
- **Versioning:** within `/api/v1` changes are additive only; a breaking change is a new `/api/v2` path with v1 kept for one release, because phones run a cached build. Events and job payloads carry `v`.
- **Errors, pagination:** one envelope and one cursor shape (SPEC §8.7), in the kernel.

**Settings screens are generated (D5).** One file `faces/settings/resources/<name>.ts` exports a `ResourceSpec`: `{ key, path, schema, columns, fields, permission, titleKey }`. `columns` and `fields` are typed as keys of the shared schema, so a renamed field fails typecheck. `CrudPage` renders the table (TanStack Table; verify; chosen over a plain `<table>` because sorting, column visibility and row virtualisation for 192 machines and 1,354 history rows would otherwise be written by hand in every pattern), search, the add and edit sheet, validation (react-hook-form with its Zod resolver; verify; chosen over React state per field because the report form and every `CrudPage` need dirty tracking, field errors from the shared schema and no re-render per keystroke on a low-end phone), disable instead of delete, and the audit line. The control defaults from the Zod type and can be overridden per field. Routes are collected from the folder, so a new settings screen adds one file and edits none. ## 6. Jobs, notifications, engine, AI

**Jobs and timers.** pg-boss is the only queue (ADR 0006). `defineJob(name, payloadSchema, handler)` per module. Enqueue on the caller's transaction; singleton key per subject; handlers are guarded no-ops when stale; a daily consistency job re-arms. Retention jobs (`session.purge`, `idempotency.purge`, `notification.purge`, `voice.retention`) are ordinary jobs owned by the table's module; none exists today.

**Calls that leave the process** always run in a job, never in a request transaction, through `kernel.withTimeout`:

| Adapter                               | Timeout | On timeout or error                                                                                 |
| ------------------------------------- | ------- | --------------------------------------------------------------------------------------------------- |
| `ChannelAdapter` push                 | 10 s    | Retry with backoff, 5 attempts, then dead letter; an expired subscription is deleted                |
| `ChannelAdapter` WhatsApp, email (M3) | 10 s    | Retry; after the last attempt, or when the monthly cap is hit, fall back to push and tell the admin |
| S3 put and get                        | 30 s    | Job retries; a PDF request shows "being prepared" and never blocks closing a ticket                 |
| Speech (M3)                           | 60 s    | 3 attempts, then the person is asked to type; the daily minutes cap is checked first                |
| `AiProvider` (M6)                     | 30 s    | No suggestion is stored; the person's flow never waits on AI                                        |

**Notification service (M2, BRIEF order 5; DOMAIN §1's "M3" label is superseded).** `notify` writes one `notification` row per recipient and channel and enqueues `notify.send` in the same transaction. `ChannelAdapter { name; canReach(person); send(message) → ok | retry | fail }`. `push` is the only adapter until M3; `whatsapp` and `email` register from the `whatsapp` module. A row stores the template key and ids, not rendered text or names; text is rendered at send in the recipient's language. `source` (kind and id) lets `accountability` ask `sentFor` who was told about an escalation, so no list of people is copied.

**Analytics engine.** `packages/engine` is pure TypeScript: `run(profile, input) → results`. The `legacy` profile reproduces Bhavin's platform at a frozen as-of date from `history_breakdown` alone (the 1,354-row Breakdown Log of the 11 November Excel export, which supersedes the 1,158 rows of the October export), with the Cosmos constants as a fixture. The `standard` profile holds improved definitions and never replaces a legacy number silently. Live figures use history rows up to the cutover date and tickets after it; a ticket matched to a history row is counted once (rule in `docs/DATA-MAP.md` §2). Results are narrow (D12): `engine_run` and `kpi_snapshot` (run, metric key, scope, period, value). `forecast` is frozen on the 1st and never rewritten. `scorecard` holds no numbers of its own: one row per month names the frozen `engine_run`, the figures chosen for the page, that month's targets, the plant head's note and who published it and when; the numbers are read from that run's `kpi_snapshot` rows.

**Python sidecar (D10): deferred** until an accepted ticket needs a model that cannot be written and tested in TypeScript within one slice.

**AI layer (M6, D16).** AI suggests; a person confirms; AI never produces a number or a code that is not already in the database.

## 8. Parallelism map
