## Blocked

The full run misses G3.2. I did not tune the limit.

`pnpm load:figures` (30 readers, 60 s, 5 years):

```
requests 457, errors 0, p50 4145 ms, p95 4449 ms, max 4781 ms, engine runs in reads 0
FAIL: p95 4449 ms is over the 300 ms limit
```

Engine runs in reads are 0 and no request failed, so the warm path from ticket 606 works. The cost is the read itself: one reader alone (`--readers 1 --seconds 8`) gets p50 208 ms, p95 249 ms. The reads are CPU-bound on one Node process, so 30 readers queue up behind each other (about 30 x 140 ms). The server needs to make one figures read much cheaper (for example less work per read than parsing and filtering the kept run each time, or caching the serialised reply per plant, date and role). That is a server change, outside this ticket's files.

## Unclear / unverified

- The board read is not loaded: there is no simple GET board route in the analytics module, so only `/api/v1/analytics/figures` is read.
- `--database-url` (checked local unless `--allow-remote`) is passed to the test harness as `TEST_PG_URL`, which makes a fresh database on that server and refuses non-local hosts. So `--allow-remote` cannot reach a remote server in practice.
- `fetch` ignores a `Host` header, so the plant is named in the URL (`load-plant.localhost`); this relies on `*.localhost` resolving to this machine.
