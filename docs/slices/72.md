The first AI feature, built on slice 55 (`docs/slices/55.md`, code in `apps/server/src/modules/ai/`). Founder direction (coordinator, 13 November): lean and functional first; no consent or production-gate work beyond 55; shadow first, plus the smallest read path that lets supervisors, the maintenance head and the admin **see** a diagnosis on staging. CLAUDE-ADOPTION lists 56 (evaluation harness) as a blocker; the founder direction overrides that for staging, and production stays shadow (§3, route rule).

## Assumptions (stated, not silent)

1. "Breakdown" means a ticket of kind `stopped`. A diagnosis is queued only when such a ticket is **raised**, not when a work request is upgraded later (product question 2).
2. "See it on staging" reads as: outside production every stored diagnosis is shown; in production only rows with `mode = 'live'` are shown, and nothing in this slice sets `live`. So production stays shadow with no new gate.
3. `tickets.search` (D22 §2) is not built yet (it moved to the search slice with `pg_trgm`, 55 decision 4). Candidates come only from `tickets.machineHistory` (this machine, then same-model machines), which D16 allows ("candidates come only from `tickets.search` and `tickets.machineHistory`").
4. The model never sees ticket ids. Code gives each past ticket a short key (`T1`, `T2`, …), keeps the key-to-id map, and turns cited keys back into ids. A uuid is long, costly in tokens, and phone-shaped to the redactor; a key outside the map is dropped (D22 §4, first check).

## 1. Goal

When a machine is reported stopped, the supervisor, maintenance head and admin see on that ticket a safety line first, then up to three likely causes, each with the past tickets behind it (or marked a guess), the cheapest first check and the expected fix.

SELECT id, code FROM machine

`machineHistory` (D22 names `{ machineId, before, limit }`; it takes a list so one function serves this machine and its siblings):

```sql
SELECT t.id, t.machine_id, t.reported_at, t.problem, t.close_note,
       r.corrective_action, r.root_cause, r.spare_used, r.maint_code, r.breakdown_category
  FROM ticket t
  LEFT JOIN LATERAL (
    SELECT corrective_action, root_cause, spare_used, maint_code, breakdown_category
      FROM breakdown_report br
     WHERE br.tenant_id = t.tenant_id AND br.ticket_id = t.id
     ORDER BY br.submitted_at DESC LIMIT 1) r ON true
 WHERE t.tenant_id = $1 AND t.machine_id = ANY($2::uuid[])
   AND t.status = 'closed' AND t.reported_at < $3
 ORDER BY t.reported_at DESC, t.ref DESC
 LIMIT $4
```

Names in `observed_by` and `handover_name` are never selected. Served by `ticket_machine_idx (tenant_id, machine_id, reported_at)`. An empty `machineIds` returns `[]` without a query.

`notesSeenElsewhere` returns which of the given notes (already normalised by `normaliseNote`) appear as the closing note of a closed ticket on a machine **outside** `outsideMachineIds`. Empty `notes` returns an empty set without a query.

```sql
SELECT DISTINCT n.note FROM (
  SELECT lower(regexp_replace(btrim(COALESCE(NULLIF(btrim(r.corrective_action), ''), t.close_note)), '\s+', ' ', 'g')) AS note
    FROM ticket t
    LEFT JOIN LATERAL (
      SELECT corrective_action FROM breakdown_report br
       WHERE br.tenant_id = t.tenant_id AND br.ticket_id = t.id
       ORDER BY br.submitted_at DESC LIMIT 1) r ON true
   WHERE t.tenant_id = $1 AND t.status = 'closed' AND t.machine_id IS NOT NULL
     AND t.machine_id <> ALL($2::uuid[])
) n
 WHERE n.note = ANY($3::text[])
```

This scans the tenant's closed tickets once per diagnosis (about 1,500 at Cosmos with history). No new index: `breakdown_report` has no `ticket_id` index today and `loadReport` already reads it the same way; an index, if the timing ever shows one is needed, goes through the architect and schema-reviewer.

Every object sets `additionalProperties: false` and lists every property as required (structured outputs; **verify** in current Anthropic docs that `required` must name every property and that `type`, `properties`, `required`, `items`, `additionalProperties` are all supported). Length and count limits (`maxItems`, `maxLength`) are deliberately left out of the JSON Schema (**verify** whether structured outputs accept them; either way they stay out) and enforced by zod: a breach is `schema_invalid` (one retry, D22). Safety comes first in property order so it is written before the causes (**verify** that generation follows schema order; correctness does not depend on it).

**`buildEvidence` rules, in order:**

1. **One outage, one row.** Within `own`, and separately within `siblings`, rows with the same `machineId`, the same UTC date of `reportedAt`, the same `normaliseNote(problem)` and the same `normaliseNote(closingNote(row))` keep only the first (newest). (Cosmos history repeats identical rows for one outage.)
2. **Template check.** A row whose `normaliseNote(closingNote(row))` is in `seenElsewhere` is left out and counted in `templatesLeftOut`: the same text on a machine of another model is a stock phrase, not evidence about this machine (skill step 3). Same text only on same-model machines is kept (a fleet pattern).
3. **Keys.** Kept `own` rows get `T1`, `T2`, … in order; kept `siblings` rows continue the numbering. `keys[key] = row.id`.
4. **Items.** `{ key, date: reportedAt.toISOString().slice(0, 10), machine (siblings only: siblingCodes.get(machineId)), problem, closeNote, action, rootCause, spare, code, category }`; a null or blank field is omitted; each string is trimmed and cut to 500 characters.
5. **Coverage.** `thisMachine` = kept own items; `withNotes` = kept own items whose `closingNote` has 3 or more whitespace-separated words ("Repaired", "OK now", "E" do not count; skill: report coverage honestly); `sameModel` = kept sibling items; `sameModelMachines` = distinct `machineId` among them; `templatesLeftOut` as in rule 2.
6. **Safety words.** `safetyWords([input.problem, ...for each kept own item: problem, closeNote, action, rootCause])`. Sibling notes are not searched: a bypass on another machine says nothing about this one.

**`safetyWords`** tests each pattern case-insensitively against every text and returns the display words found, distinct, in list order (Cosmos: notes with "bypass" or "temporary solution" are safety-relevant; product question 3 confirms the list):

| Display word    | Pattern (flag `i`)                          |
| --------------- | ------------------------------------------- |
| `bypass`        | `\bby-?pass`                                |
| `jumper`        | `\bjumper`                                  |
| `temporary fix` | `\btemporary\b\|\btemp (?:fix\|solution)\b` |
| `jugaad`        | `\bjugaa?d`                                 |
| `short circuit` | `\bshort[- ]?circuit\|\bshorted\b`          |
| `spark`         | `\bspark`                                   |
| `smoke`         | `\bsmok`                                    |
| `burn`          | `\bburn`                                    |
| `shock`         | `\bshock`                                   |
| `interlock`     | `\binterlock`                               |
| `guard`         | `\bguard`                                   |

**`groundAnswer`** (D22 §4; the second check, the tenant re-read, is done by the caller and passed in as `visible`):

- A cited key is normalised: trimmed, one leading `[` and one trailing `]` removed, upper-cased. Within a candidate a repeated key counts once.
- A key not in `keys`, or whose id is not in `visible`, is dropped and adds 1 to `dropped`. Kept ids keep citation order, at most 8.
- `isGuess = evidenceTicketIds.length === 0` (set by code, never by the model).
- `safetyFlagged = answer.safetyFlagged || safetyWords.length > 0`. `safetyReason` is the model's when it flagged; when only code flagged, `` `Notes on this machine or this report mention: ${words.join(', ')}.` ``; otherwise the model's text.
- `output = { v: 1, safetyFlagged, safetyReason, safetyWords, candidates, coverage }`; `evidenceTicketIds` is the distinct union over candidates, in order.

`citedIds` returns the distinct ids that the normalised cited keys map to (the ids `ground` re-reads with `tickets.refsByIds`).

### The prompt `ai/prompts/diagnosis.md` (72b)

First line is the version marker; the rest is sent as `task` (the system text). The version is the file's, so a prompt change is a version change and a new `ai_suggestion` key (D22 §9). Exact text:

```markdown
<!-- prompt: diagnosis · version: diagnosis-1 -->

You help the maintenance team of a machining plant work out why a machine has stopped. You suggest; a person decides. Code checks your answer and shows it on the ticket under a fixed lockout line that the app writes, so do not write a lockout line yourself.

## What you get

One JSON object:

- `ticket`: the new breakdown: the problem as the reporter wrote it, the date reported, and the machine (code, make, model, category) when known.
- `thisMachine`: closed past tickets on this machine, newest first. Each has a `key` (T1, T2, …), a `date`, and what was written: `problem`, `closeNote`, `action` (what was done), `rootCause`, `spare`, `code`, `category`.
- `sameModel`: closed past tickets on other machines of the same make and model (`machine` is that machine's code), newest first, keys continuing the numbering.
- `coverage`: how many past tickets were found and how many have a useful note. Notes whose exact words also appear on machines of other models were left out already: they are stock phrases, not evidence about this machine.

People appear as [P1], [P2]; a phone number as [PHONE]; the plant as [PLANT]. Keep them as they are and never guess who they are.

Notes mix English with Gujarati or Hindi words in Latin letters, for example "chalu" (running), "band" (stopped), "jugaad" (a makeshift fix). Read them for meaning. A one-letter `code` such as E or M says only electrical or mechanical; it is not a cause.

## Safety first

Set `safetyFlagged` to true when the ticket or this machine's past tickets show any of these:

- a seized or locked rotating part: spindle, chuck, bar feeder, conveyor
- a guard or interlock that is defeated, bypassed or failed
- a bypass, jumper, temporary or makeshift fix that may still be in place
- stored energy: springs, counterweights, a part under load, a raised axis
- hydraulic or pneumatic pressure that has to be bled before work
- an electrical fault: a trip, a burnt smell, sparks, exposed or damaged wiring
- a fault cleared by restarting rather than fixed, now repeating

Then write which one in `safetyReason`, quoting the words and naming the key, for example "T3 says the door interlock was bypassed". When none is shown, `safetyFlagged` is false and `safetyReason` is "None of the safety triggers shown." Never set the flag on a feeling. Never leave it off because you are unsure: an uncertain stored-energy hazard is a safety implication.

## Likely causes

Give at most three, most likely first. For each:

- `cause`: the likely cause, in one plain sentence.
- `evidence`: the keys of the past tickets it rests on. Look at this machine first, then the same model. A past ticket with the same symptom outweighs a recent one with a different symptom. "Again", "still", "same as last time" and "temporary" mean a fault was not really fixed. Cite only keys from the input. A `sameModel` ticket is a pattern on that model. If nothing in the input supports the cause, leave `evidence` empty and the app will show it as a guess; a guess from experience is welcome, but do not dress it up as evidence.
- `firstCheck`: the cheapest, fastest check that tells this cause apart from the next one.
- `expectedFix`: what will probably fix it, and the repair path.

If two causes are equally supported, give both; do not break the tie.

## Be honest about thin history

Terse notes such as "fixed", "repaired" or "ok now" are not evidence of a simple repair. If the history is thin, say so in the cause or the first check rather than over-reading it. Do not invent ticket keys, part numbers, readings, durations or counts that are not in the input.

## Style

Short, plain English that a technician reads on a phone. No headings and no markdown. Answer only in the output format.
```
