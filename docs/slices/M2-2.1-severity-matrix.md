# M2‑2.1 — Severity matrix

## Scope and decision

Implement the severity matrix as defined in `docs/spec/DOMAIN.md` §Severity: a plant‑configurable mapping from machine criticality (A, B, C) and ticket kind/urgent flag to a severity level S1–S4. Severity is computed when a ticket is created (or when its machine criticality changes) and stored on the ticket as a non‑nullable `severity` column; the machine’s criticality at report time is saved as `criticality_snapshot`. The mapping is configurable per tenant in Settings, with a default matrix that exactly matches the spec.

This slice is a foundation for M2‑2.2 (SLA timers) and M2‑2.3 (escalation), which will use the severity to set timers and escalation rules.

**Out of scope:** SLA timers, escalation rules, handback, per‑severity UI styling beyond the existing ticket detail.

**Previously present in schema:** The `ticket` table already has nullable `severity` and `criticality_snapshot` columns; the `machine` table already has a `criticality` column (A, B, C). No migration step alters these column definitions, but they become enforced by the domain and API.

## Public contract

`Severity = 'S1' | 'S2' | 'S3' | 'S4'`.
`Criticality = 'A' | 'B' | 'C'`.

`SeverityMatrix = { default: Record<Criticality, Record<'stopped' | 'support', Severity>>, workRequest: Severity, urgentWorkRequest: Severity }`.

Server-side calculation:

- `computeSeverity(matrix: SeverityMatrix, machineCriticality: Criticality | null, kind: 'stopped' | 'support' | 'general', urgent: boolean): Severity`.
  - If `machineCriticality` is `null` (general work request), use `urgent ? matrix.urgentWorkRequest : matrix.workRequest`.
  - Else look up `matrix.default[machineCriticality][kind]`.
- The function lives in `packages/domain/src/severity.ts`; no I/O, 100% unit‑tested.
- The tenant’s matrix is loaded via `/api/config` (already includes machines with criticality); a Settings screen edits the matrix and stores it as a `setting` row with key `'severity_matrix'`.

API additions:

- `GET /api/config` unchanged; the matrix is part of the tenant’s config, loaded like other settings.
- `POST /api/settings/severity-matrix` with `SeverityMatrix` → stores the matrix; triggers a config fingerprint change.
- No separate severity endpoint; severity is computed and stored on the ticket at creation/update, and appears in ticket detail.

Ticket commands (`start`, `transfer`, `pause`, `close`, `correct`) recalculate severity if `machine_id` or `kind` changes, but the stored snapshot remains unchanged (criticality is captured at report time). A `correct` that changes the machine uses the new machine’s current criticality for future calculations but does not alter the snapshot.

## Data and module boundaries

**New files/modules:**

- `packages/domain/src/severity.ts`: pure `computeSeverity` function, unit tests.
- `packages/domain/src/types.ts`: add `Severity`, `Criticality`, `SeverityMatrix` types.
- `packages/shared/src/config.ts`: add `severityMatrixSchema` (Zod) and wire types.
- `apps/server/src/config.ts`: load the matrix from `setting` table; include it in the config payload.
- `apps/server/src/settings/severity-matrix.ts`: route to update the matrix (admin‑only).
- `apps/server/src/ticket/severity.ts`: helper that calls the domain function and stores the result on ticket updates.
- `apps/web/src/components/settings/SeverityMatrix.tsx`: Settings screen that shows/edit the matrix.
- `apps/web/src/components/TicketDetail.tsx`: show severity badge (S1–S4) and criticality snapshot.

**Existing modules touched:**

- `packages/db/src/tables.ts`: add `severity` and `criticality_snapshot` constraints (NOT NULL after migration).
- `apps/server/src/ticket/commands.ts`: call severity helper after each command that could affect severity.
- `apps/server/src/ticket/sql.ts`: store severity/criticality_snapshot on insert/update.
- `apps/web/src/api-types.ts`: add types for severity matrix.
- `apps/web/src/components/settings/SettingsLayout.tsx`: add SeverityMatrix tab.

**Database:**

- No new tables. `ticket.severity` and `ticket.criticality_snapshot` remain as they are; we add a `CHECK` constraint to enforce S1–S4 and A/B/C/null.
- The matrix is stored in `setting` table with key `'severity_matrix'`, JSONB.
- Migration: `packages/db/migrations/0006_severity_matrix.sql` adds the CHECK constraints and a default matrix row.

## Tests (Given / When / Then)

Each case exercised through the public API, real database, or real browser.

1. **Domain calculation:** Given the default matrix and various (criticality, kind, urgent) combinations, when `computeSeverity` is called, then it returns the spec‑defined S1–S4.
2. **Custom matrix:** Given a tenant‑modified matrix, when tickets with different criticality/kind are created, then severities follow the custom matrix.
3. **Ticket creation:** Given a machine with criticality A and a stopped report, when the ticket is created, then `severity='S1'` and `criticality_snapshot='A'`.
4. **Machine‑less ticket:** Given a general work request with urgent=true, when created, then `severity='S3'` (urgentWorkRequest).
5. **Configuration load:** Given a stored custom matrix, when `/api/config` is fetched, then the matrix appears in the payload and the fingerprint changes.
6. **Settings update:** Given an admin, when they POST a new matrix, then the setting is stored and future tickets use it.
7. **Correct command:** Given a ticket with machine A, when `correct` changes machine to B, then `severity` is recalculated (now B‑stopped → S2) but `criticality_snapshot` stays 'A'.
8. **Concurrent config change:** Given two tickets created while the matrix is being updated, then each ticket uses the matrix that was current at its creation.
9. **Invalid matrix validation:** Given a POST with missing keys or invalid severity values, then 422 with clear errors.
10. **Tenancy isolation:** Given tenants A and B with different matrices, when each creates a ticket, then severities match each tenant’s matrix.

### Implementation notes (as built)

- Severity is derived at raise time in `apps/server/src/ticket/severity.ts :: buildRaiseExtras`
  using the machine's criticality snapshot. It is **not** a tag; the M2 tag boundary is unchanged.
- `correct` (machine/kind change) and `upgrade-kind` recalculate via `refreshSeverity`, called from
  `executeCommand` before `persistResult`. The snapshot follows the corrected machine's criticality.
- A machine with no criticality falls back to C (lowest) per `computeSeverity`.
- Tickets keep `severity` and `criticality_snapshot` columns from schema v1; migration
  `0006_severity_matrix.sql` adds CHECK constraints and seeds the default matrix per tenant.
- The Settings screen is a new route `/desk/settings`, linked from the desk header for admin/head.
