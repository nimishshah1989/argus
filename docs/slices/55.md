## 1. Goal

Staging can send one ticket's text to Claude and keep the answer as a stored suggestion: names, usernames, phone numbers and the plant's name are removed first, each try and its cost are recorded, the month's spend is capped, and the same suggestion is never paid for twice. No one sees anything new yet; diagnosis on the ticket (ticket 72) is the first feature built on this.

### `identity.redactionTerms`

```ts

  shortNames: string[]; // person.short_name, non-null
```

Three queries: `SELECT name, short_name, phone FROM person WHERE tenant_id = $1`; `SELECT username FROM login WHERE tenant_id = $1`; `SELECT name FROM tenant_info($1)`. ### Redactor `ai/redact.ts`

```ts
export interface Redactor {
  redact(value: AiJson): AiJson; // replaces in every string leaf, returns a new value
  leaks(text: string): boolean; // true if any term or phone-shaped number is present
}
export function createRedactor(terms: RedactionTerms): Redactor;
```

Rules, all inside the closure (the placeholder map is never returned, stored, logged or sent):

- People terms are `names`, `shortNames` and `usernames`. Terms shorter than 2 characters are ignored by both `redact` and `leaks`. Terms are matched longest first, case-insensitively, with Unicode word edges: `(?<![\p{L}\p{N}])<escaped term>(?![\p{L}\p{N}])`, flags `giu` (works for Gujarati script, where `\b` does not).
- Each distinct people term (case-folded) gets `[P1]`, `[P2]`, … in order of first replacement within this redactor. `tenantName` becomes `[PLANT]`. Each stored phone, and any phone-shaped number, becomes `[PHONE]`. Phone shape: `/(?<!\d)\+?\d(?:[\s-]?\d){9,13}(?!\d)/g` (10 to 14 digits, spaces or hyphens allowed between them).
- Placeholders are never turned back into names (D22 §5).

### Provider `ai/provider.ts`

```ts
export type AiJson = string | number | boolean | null | AiJson[] | { [key: string]: AiJson };
export interface AiOutputSchema<T> {
  name: string;                         // tool name, /^[a-z_]{1,64}$/
  description: string;
  jsonSchema: Record<string, unknown>;  // hand-written JSON Schema sent to the model
  zod: z.ZodType<T>;                    // the reply is always validated with this (D22 §10)
  example: T;                           // what the fake provider returns by default
}
export interface AiCompleteRequest<T> { task: string; input: AiJson; outputSchema: AiOutputSchema<T> }
export interface AiUsage { inputTokens: number; outputTokens: number }
export interface AiCompleteResult<T> { output: T; usage: AiUsage; modelRef: string }
export interface AiProvider {
  readonly modelRef: string;            // stored on the row at claim, before the call
  complete<T>(request: AiCompleteRequest<T>): Promise<AiCompleteResult<T>>;
}
export type AiProviderErrorCode =
  'provider_error' | 'rate_limited' | 'overloaded' | 'provider_rejected' | 'schema_invalid';
export class AiProviderError extends Error {
  constructor(readonly code: AiProviderErrorCode,
              readonly usage: AiUsage = { inputTokens: 0, outputTokens: 0 },
              readonly retryAfterSeconds: number | null = null);
}
export type FakeReply = { output: unknown; usage?: AiUsage } | AiProviderError;
export interface FakeProvider extends AiProvider { readonly calls: AiCompleteRequest<unknown>[] }
export function createFakeProvider(replies?: FakeReply[]): FakeProvider;
export function pickProvider(config: AiConfig, fetchImpl?: typeof fetch): AiProvider;
```

- `AiJson` has no binary or image member: text only (D22 §6).
- The fake's `modelRef` is `'fake'`. Each call pushes the request to `calls`, then takes the next reply in order: an `AiProviderError` is thrown; an output is validated with `zod` (failure throws `schema_invalid` carrying the reply's usage); with no replies left it returns `example` with zero usage.
- `pickProvider` returns `createClaudeProvider({ apiKey, model, maxOutputTokens, timeoutMs, fetchImpl })` when `config.apiKey` is set; else, outside production, `createFakeProvider()`; in production with no key it returns `null`, and the job settles nothing and makes no call (no `fake` row ever exists in production). [decision 5]

One `POST` per call, `signal: AbortSignal.timeout(timeoutMs)`. The structured-output mode is a **single forced tool call** whose input is the answer (D22 §10's named fallback; still one request, the model gets no data-fetching tool and cannot ask for more, so D22's rejection of a tool-use loop does not apply). Chosen over JSON-schema output because it is the long-standing Messages API shape; moving to JSON-schema output later is a change inside this file only.

Every item below is **verify in current Anthropic docs** before coding. If any differs, the coder stops and returns the difference to the planner; nothing is guessed.

| Item                 | Planned value                                                                                                                                                                                      |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| URL                  | `https://api.anthropic.com/v1/messages`                                                                                                                                                            |
| Headers              | `x-api-key: <key>`, `anthropic-version: 2023-06-01`, `content-type: application/json`                                                                                                              |
| Body                 | `{ model, max_tokens, system: task, messages: [{ role: 'user', content: JSON.stringify(input) }], tools: [{ name, description, input_schema: jsonSchema }], tool_choice: { type: 'tool', name } }` |
| Success              | HTTP 200; the answer is the `input` of the `content` block with `type: 'tool_use'` and `name` = the schema's name; tokens from `usage.input_tokens`, `usage.output_tokens`                         |
| Cut short, refused   | `stop_reason` `max_tokens` or `refusal`                                                                                                                                                            |
| Rate limit, overload | HTTP 429 with a `retry-after` header in seconds; HTTP 529                                                                                                                                          |
| Provider console cap | A monthly spend limit can be set per workspace in the console (D22 backstop); the operator sets it                                                                                                 |

Mapping to `AiProviderError` codes (D22 failure table): fetch rejects (abort, timeout, network) → `provider_error`; 429 → `rate_limited` with `retryAfterSeconds` from the header (integer seconds, else null); 529 → `overloaded`; other 5xx → `provider_error`; any other non-200 (400, 401, 403, 404, 413 …) → `provider_rejected`; 200 with a body that is not JSON → `provider_error`; 200 with `stop_reason` `max_tokens` or `refusal`, no matching `tool_use` block, or an `input` that fails `zod` → `schema_invalid` carrying the reply's usage. Error messages name only the code and HTTP status; never the key, the request body or the response body.

### Limits `ai/limits.ts` (pure)

```ts
export type RetryStep = { kind: 'retry'; afterSeconds: number } | { kind: 'fail' };
export function retryPlan(
  code: AiProviderErrorCode | 'redaction_failed',
  attempts: number,
  retryAfterSeconds: number | null,
): RetryStep;
export function costMicroUsd(usage: AiUsage, config: AiConfig): number;
export function maxCallCostMicroUsd(promptBytes: number, config: AiConfig): number;
export function monthStartUtc(now: Date): Date;
```

`attempts` is the row's total provider calls including this one (the row is the truth, D22). `retryPlan`:

| Code                                    | Retry while `attempts` < | Wait before the next attempt                                                         |
| --------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------ |
| `provider_error`                        | 3                        | after attempt 1: 30 s; after attempt 2: 120 s                                        |
| `rate_limited`, `overloaded`            | 4                        | `min(retryAfterSeconds, 600)` when given; else after attempt 1, 2, 3: 60, 120, 240 s |
| `schema_invalid`                        | 2                        | 30 s (the table gives no wait; planner decision)                                     |
| `provider_rejected`, `redaction_failed` | never                    | —                                                                                    |

The limit counts all attempts on the row, whatever earlier attempts returned: a 429, then a 529, then an invalid reply ends `failed` after 3 calls, because `schema_invalid` allows 2. No row ever exceeds 4 calls.

`costMicroUsd = ceil(inputTokens × priceInputUsdPerMtok + outputTokens × priceOutputUsdPerMtok)` (1 USD per million tokens is 1 micro-USD per token). `maxCallCostMicroUsd = ceil(promptBytes × priceInput + maxOutputTokens × priceOutput)`: a token is at least one byte, so the UTF-8 byte length of `task + JSON.stringify(input)` bounds the input tokens from above.

```ts
  costMicroUsd: number;
  now: Date;

  id: string,
  s: Settlement,

export async function monthCostMicroUsd(tx: Db, tenantId: string, since: Date): Promise<number>;
```

`claimSuggestion` is one statement:

```sql
INSERT INTO ai_suggestion (tenant_id, feature, subject_type, subject_id, ticket_id, prompt_version,
  model_ref, status, created_at, updated_at)
VALUES ($1, $2, $3, $4, $5, $6, $7, 'running', $8, $8)
ON CONFLICT (tenant_id, subject_type, subject_id, feature, prompt_version) DO UPDATE
  SET status = 'running', updated_at = EXCLUDED.updated_at
  WHERE ai_suggestion.status = 'retry_wait'
     OR (ai_suggestion.status = 'running'
         AND ai_suggestion.updated_at < EXCLUDED.updated_at - interval '90 seconds')
RETURNING id, attempts
```

No row returned means `duplicate`. A concurrent second insert waits on the unique index and then returns no row. The 90-second lease (30 s call timeout plus margin) lets a job re-run after the process died mid-call (D22: "the retry calls again; `attempts` was raised before the call"). `settleSuggestion` adds usage and cost to the row's running totals (`input_tokens = input_tokens + $n`, and so on), so tokens of failed tries are still counted. `monthCostMicroUsd` is `SELECT COALESCE(sum(cost_micro_usd), 0)::bigint … WHERE tenant_id = $1 AND created_at >= $2` (served by `ai_suggestion_month_idx`), returned as a JavaScript number.

`runSuggest`, in order **[review]: gates, then claim, then redaction scan, then call**:

1. Parse with `aiSuggestPayloadSchema`. Invalid: throw (pg-boss fails the job; nothing logged from the payload). Start the duration clock.
2. `feature_off` if `rt.features[payload.feature]` is absent or its `promptVersion` differs from the payload's.
3. Transaction 1, `withTenant(pool, payload.tenantId, …)` (tenant only from the payload, D22 §3):
   - If `config.production`: `plant.setting(tx, tenantId, 'ai.consent')` must parse with `aiConsentSchema` and be `granted`, else `no_consent`; `plant.setting(tx, tenantId, 'ai.monthlyCapUsd')` must parse with `aiMonthlyCapUsdSchema`, else `cap_reached`.
   - `feature.load(tx, tenantId, subjectId)`; `'stale'` → `stale`.
   - `identity.redactionTerms(tx, tenantId)`; `createRedactor`; `redacted = redactor.redact(input)`.
   - Cap: `cap = setting ?? config.defaultMonthlyCapUsd` (outside production the setting is used when valid, else the default). If `monthCostMicroUsd(tx, tenantId, monthStartUtc(now)) + maxCallCostMicroUsd(bytes(task + JSON.stringify(redacted)), config) > cap × 1,000,000` → `cap_reached`.
4. Transaction 2 (claim and scan, one transaction): `claimSuggestion` (`ticketId = subjectId`); null → `duplicate`. If the claimed row already has 4 attempts: settle `failed` / `provider_error`, no call. If `redactor.leaks(task + '\n' + JSON.stringify(redacted))`: settle `failed` / `redaction_failed` with zero usage and no `markAttempt` (attempts stays as it was; a later job for the same key is a `duplicate`, so the alarm-worthy line is written once). Else `markAttempt`.
5. No transaction open: `provider.complete({ task, input: redacted, outputSchema })`.
6. Transaction 3: success → settle `ready` / `ok` with the output and cost. `AiProviderError` → `retryPlan(code, attempts, retryAfterSeconds)`: `retry` → settle `retry_wait` with that code and the usage, and in the same transaction `boss.send(AI_SUGGEST_QUEUE, payload, { startAfter: afterSeconds, db: jobDb(tx) })`; `fail` → settle `failed` with that code and the usage. Any other thrown error propagates (pg-boss retries once; the lease allows it).
7. Write exactly one `AiLogLine` for every return path (`suggestionId` null and tokens 0 where no row was claimed; `evidenceDropped` is 0 in this slice: evidence checks belong to each feature). Return the outcome.

A stale or gated retry leaves its row in `retry_wait` with the last error outcome; nothing reads that row in this slice. `cap_reached` is only logged **[review]**: no `notify` call (ticket 32 is M2) and no dependency on it.

### Not changed

`AiProvider.complete({ task, input, outputSchema }) → { output, usage, modelRef }` keeps D22's shape; `modelRef` is also exposed as a property so the row can name the model before the call. `kernel.withTimeout` is not built: `AbortSignal.timeout` does the one timeout this slice needs (LEAN rung 3).
