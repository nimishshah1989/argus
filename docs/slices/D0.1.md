# D0.1 — Current-truth audit, role journeys and visual-direction contract

## Goal

Capture the existing frontend as unapproved functional scaffolding, audit it against Bhavin v3 and the
four analytics inventories, document one journey per role, and freeze the direction for D0.2/D0.3.
This slice creates documentation and evidence only. It does not reskin a production screen or approve
the current UI.

## Authoritative direction from Nimish (11 November 2026)

Apply Apple's **clarity, deference and depth** literally. Body/canvas and cards are **white**; neutrals
are for text, borders and subordinate detail, not a grey application background. Use one deep-teal
action accent, semantic red/amber/green states, one Lucide outline icon family, and progressive
disclosure.

- **Clarity:** one primary action; icon + text, never colour alone; 52 px Floor/Desk targets; WCAG AA.
- **Deference:** borders before shadows; no decoration that does not help the task; no competing
  blue/violet rainbow, gradients, glass, dark variant or display font in v0.
- **Depth:** sheets/expanded details explain hierarchy. Timelines, people, figures, corrections and
  history remain available underneath rather than disappearing for visual simplicity.
- **Icons:** Lucide outline only, 1.75 px stroke/round joins; 16 status, 20 button/list, 24 navigation,
  28 Floor choice. Decorative icons are hidden from assistive technology; icon-only controls have
  accessible names and 52 px targets.
- **Colour:** deep teal = action/selection/focus/working; red = stopped/destructive; amber = support,
  follow-up, waiting/transferred-for-pickup; green = running/success; neutral = general/not-started/
  cancelled and other inactive detail.

### Exact two-axis status contract

Condition and work are independent and each gets icon + label. Example: **Stopped · In progress**.

| Axis             | Source fields                                              | Mapping                                                                                                                                                                                                                                                                                    |
| ---------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Condition        | `kind`, `parentId`, `machineRunningAt`, `machineStoppedAt` | `support` → amber LifeBuoy **“Support”**; `general` with parent → amber ClipboardCheck **“Follow-up”**; other general → neutral ClipboardList **“Work request”**; `stopped` → red CircleStop **“Stopped”**, except a later running interval → green CircleCheck **“Running”**              |
| Running interval | `machineRunningAt` and `machineStoppedAt`                  | running-again only when running exists and is later than stopped (or stopped is null); a running machine does not close the ticket                                                                                                                                                         |
| Work             | `status`, `handedOver`                                     | closed → green CheckCheck **“Closed”**; cancelled → neutral CircleX **“Cancelled”**; waiting → amber Clock3 **“Waiting”**; working → teal Wrench **“In progress”**; open + handedOver → amber ArrowRightLeft **“Waiting for pickup”**; other open → neutral CircleDashed **“Not started”** |

### Delegated prototype decisions and their honest production state

1. Show both condition and work state; transferred remains open/waiting-for-pickup, not a stored status.
2. **Offline new stopped/support reports:** design as queued with a visible pending state, a persisted
   client idempotency key reused on every replay, duplicate-open resolution to the existing ticket, and
   visible unresolved-failure/needs-attention behavior. **Other-work/general is excluded and requires a
   connection until separately approved.** Production implementation is a separate M1 todo slice.
3. **My complaints:** acting-person scoped, with no device-wide history and no Desk link for report-only
   users. Filtering already exists through `raisedBy=<actingPersonId>`; shared-phone and no-Desk-link
   evidence is still prototype-only/pending. Existing evidence is not deleted or marked complete.

Nimish delegated these recommendations to the lead. The latest white/deep-teal/red-amber-green
instruction supersedes older grey/blue/violet hints in the audit and normative docs.

## Baseline capture interface

Use existing `signIn`, `apiLogin`, `raiseTicketViaApi` and `MACHINES[4]` from `apps/web/e2e/fixtures.ts`
with fake `asha` only. The isolated config gives this spec exclusive use of a fresh fake stack; no other
spec runs concurrently and no fixtures change. One ordered test reuses the same page/ticket throughout.

```ts
async function captureRoute(input: {
  page: Page;
  id: string;
  route: string;
  role: 'anonymous' | 'technician';
  state: string;
  width: 360 | 1440 | 1920;
  height: 800 | 1000 | 1080;
  machineCode?: 'VC-5';
}): Promise<BaselineEntry>;
```

`BaselineEntry` contains `id`, `route`, `role`, `state`, `viewport: {width,height}`,
`image: {width,height}`, `file`, `machineCode: string|null`, `refPattern: string|null`. Capture full
page with motion disabled after fonts and two animation frames settle. Viewport pairs are exactly
360×800, 1440×1000, 1920×1080. After each capture, read its PNG IHDR and record the actual image
width/height in `image`; full-page height may exceed the viewport.

Ordered cases:

1. `/login`, anonymous/default: assert Sign in; capture 360 and 1440.
2. `/floor`, technician/report: `signIn(page, 'asha')`; assert Report a problem; capture 360 and 1440.
3. API-raise on `MACHINES[4]` (VC-5), `/desk`, technician/open: assert the ref link; capture 360/1440.
4. `/desk/{ticket.id}`, click Start, technician/working: assert In progress; capture 360/1440.
5. Same authenticated session, `/desk/board?kiosk=1`, technician/kiosk: assert no navigation links and
   the VC-5/ref tile; capture 1920 only.

Dynamic refs/timestamps are allowed because these are current-truth evidence, not pixel goldens. Assert
machine/ref/state exactly. Only when `D01_CAPTURE=1` is explicitly set does the first test write images
and candidate entries to ignored `tmp/d01-candidate.json` (Playwright cleans `test-results` between
invocations, so candidate evidence must not live there); it never writes the final manifest.
On the later complete run without that variable it repeats the route assertions but writes nothing, so
the already-inspected PNGs cannot be overwritten with a new ticket/timestamps.

Final manifest shape:

```ts
interface BaselineManifest {
  schemaVersion: 1;
  sourceCommit: string;
  visualApproval: false;
  fakeData: 'Playwright E2E fixtures only';
  captures: BaselineEntry[];
}
```

After the capture test, the agent opens **all nine images with an image reader**, rejects blank,
wrong-state or font-broken captures and only then writes the final manifest with the current source
commit. Playwright must not claim that human/agent visual inspection happened.

## Numbered red → green tests and reviewer checks

1. **`captures current-truth routes in one ordered session`** — Given a fresh fake stack, when the five
   routes/states above are visited, then nine correctly named images and candidate entries are produced
   and machine/ref/state assertions pass. Run this test alone first to generate evidence.
2. **`verifies all nine baseline images and manifest entries`** — Given no final manifest initially,
   when verification runs before agent inspection, then it fails (RED). After the agent writes the
   manifest, the test reads it and asserts schemaVersion/sourceCommit/visualApproval/fakeData, exact nine
   ids/routes/roles/states/viewports/files, each PNG signature, and each PNG's IHDR width/height using
   Node's built-in buffers only. IHDR must equal the recorded `image` dimensions, `image.width` must
   equal `viewport.width`, and full-page `image.height` must be at least `viewport.height` (GREEN).
   Candidate files do not satisfy this test.
3. **Manual role/status/decision checklist (fresh design reviewer):** every role has one primary job,
   five total first-screen items, all five states and progressive detail; management has exactly the
   five agreed outcomes; the two-axis matrix matches domain fields and icon/colour/label semantics;
   every literal label above is repeated unchanged in DESIGN, FRONTEND-STRATEGY, SPEC and ROLE-JOURNEYS;
   offline stopped/support remains todo with general excluded; acting-person filtering is described as
   existing while shared-phone/no-Desk-link evidence stays pending; the legacy/inventory map covers all
   parity sections without copying implementation.
4. Run these in order, with the regular E2E stack stopped:
   - Capture: `D01_CAPTURE=1 pnpm exec playwright test --config playwright.baseline.config.ts --grep "captures current-truth routes"`; all nine PNGs and the tmp candidate now exist.
   - Ensure the final manifest is absent, then RED:
     `pnpm exec playwright test --config playwright.baseline.config.ts --grep "verifies all nine baseline images"`. With all nine PNGs present, it must fail specifically because the final manifest is absent.
   - Open all nine images, then write the final manifest.
   - GREEN: `pnpm exec playwright test --config playwright.baseline.config.ts --retries=0` **without**
     `D01_CAPTURE`; both tests run, the capture test repeats assertions without writes, and verification
     checks the exact inspected files. Report zero skip/fixme/only and zero skipped tests.
5. Run `pnpm exec playwright test --retries=0`, `pnpm verify`, `pnpm parity`, and `pnpm parity:update`.
   `parity:update` is only a diff guard, not a generator. No flake is retried into green.
