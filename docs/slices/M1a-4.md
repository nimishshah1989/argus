# M1a-4 — Tickets API

## Goal

The full ticket command API over the already-written `packages/domain` `transition()` and
`raiseTicket()`, with `FOR UPDATE` row locks, `Idempotency-Key` replay, `GET /state` and
`GET /tickets/{id}`. Shipped as one PR, plus a separate EIP-only infra PR (item 0).

## Cross-cutting contract

- **Auth**: `requireAuth` first. Personal login may act only as its own person; a shared login
  may act as any active person in the tenant (body `personId`, validated to exist).
- **Row locks**: every command runs inside `withTenant`; the ticket row is loaded
  `SELECT … FOR UPDATE` before events/segments/crew are read and the transition applied and
  committed in one transaction. A concurrent command serialises and re-validates.
- **Idempotency**: header `Idempotency-Key` required on every mutating `POST`. First run stores
  `{status, body}` under `command_idempotency(tenant_id, key, command, result)`; a repeat returns
  the stored result without re-executing. Events also carry `ticket_event.idempotency_key`.
  Missing header → 422 with `field: 'idempotencyKey'`.
- **Figures**: after `raiseTicket`/`transition`, recompute `figures()` and persist
  `response_min, active_min, wait_min, vendor_min, handover_wait_min, down_acc_min, downtime_min,
follow_min, repair_min`; return the `figures` object on the ticket.
- **Errors** `{error:{code, message, field?}}`: permission denied → 403 `forbidden`; invalid
  state → 409 `conflict`; unknown id / other tenant → 404 `not_found`; bad body → 422
  `validation`. Map `TransitionError` ("Not allowed*") → 403, other `TransitionError` → 409.

## Test cases (Given / When / Then)

1. Raise a stopped ticket → 201, `BD-` ref, appears in `/state`.
2. Raise a `general` task (no machine) → 201; `general` without location/workType → 422.
3. Raise a duplicate open ticket on the same machine → 409 `conflict`.
4. Full happy path: raise → start → pause → resume → machine-running → machine-stopped →
   update → transfer → start(pickup) → join → leave → close. Each returns the ticket with the
   new status; figures are non-null and monotonic where defined.
5. Permission: operator cannot start/pause/close → 403; technician can; close by non-crew
   technician → 403.
6. State conflicts: start a working ticket → 409; resume a non-waiting ticket → 409.
7. `GET /tickets/:id` returns the event log, crew, segments and (empty) tasks.
8. Idempotency: replay the same command with the same `Idempotency-Key` returns the identical
   status and body, and applies once (event count unchanged); raise replay returns the same ref.
9. Row-lock concurrency: two concurrent `start` commands on one open ticket → one 200, one 409;
   two concurrent raises with one `Idempotency-Key` → one ticket, both same ref.
10. Cross-tenant: a ticket id from another tenant → 404.
11. Missing `Idempotency-Key` on a command → 422.
