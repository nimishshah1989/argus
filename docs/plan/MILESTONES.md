Rules: one ticket = one vertical slice = one GitHub issue = one slice plan = one PR (≤ ~800 changed lines; the slice-planner splits a larger one and says why). Process and doc tickets exist only in H, with two prescribed exceptions: M4a-01 (triage with Bhavin) and M6-00 (AI alignment with Nimish). A design-system ticket precedes every new screen. No ticket depends on M3. Each milestone's schema lands first as one migration ticket in the schema lane. Real Cosmos data is used for all testing on staging (India); CI, which runs outside India, uses only the pseudonymised fixture set (S9). AI runs in shadow until its threshold; numbers come from code, never from a model. M5 (second plant) is deferred: nothing is planned for it. "Verify" marks a library or extension not yet installed: the slice-planner checks its current documentation before naming any function from it.

Already done on 13 November, so not tickets: ROADMAP H4 and H5 (architecture, data map, brief); the stop hook (`fast-tests.sh` runs 161 DB-free tests in about 2 s); Nimish's answers to the DATA-MAP questions (recorded in `BRIEF.md` "Decided" and `DATA-MAP.md` "Answered by Nimish").

## 4. Goal-loop contract

**One ticket = DEFINE → CODE → TEST → BUILD.** The GitHub issue is the persisted goal (goal, acceptance, depends, area, lane, wave in its body).

| Step         | Athena role                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Done when                                                                                                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DEFINE       | Orchestrator marks the issue `ready-for-agent` (deps merged, lane free, external satisfied; otherwise `blocked-external` and take the next). `slice-planner` (Opus) writes `docs/slices/<issue>.md`: every file, interface, data field and Given/When/Then test that fails first, regression risk, "verify" checks. `plan-reviewer` (Opus, fresh context) reviews. If `schema?` = Y, or a contract, module or public route changes: `architect` (Fable) + `schema-reviewer` / `architecture-reviewer` (Opus) | plan-reviewer PASS (and schema/architecture PASS where needed; data-altering migrations carry a backup step and the `approved-by` / `backup:` header). A product gap becomes a PQ for Nimish; a technical gap is decided by agents |
| CODE         | Sonnet with `tdd` + `subagent-driven-development`, on a branch. **Ponytail:** the smallest change that meets the acceptance; nothing the plan does not name; LEAN limits (400-line file, 60-line function, no dependency without an ADR)                                                                                                                                                                                                                                                                     | Failing tests committed first, then the code that makes them pass; no test deleted, skipped or weakened                                                                                                                            |
| TEST         | Stop hook runs the fast tests (`fast-tests.sh`, 161 DB-free tests, ~2 s) at every stop; the whole suite (DB tier on Testcontainers) before review; CI runs lint, types, unit, DB, sharded E2E, gallery screenshots + axe, `check-boundaries`, `check-ui`, `check-migrations`, parity, licences, PII scan — on the S9 pseudonymised fixtures                                                                                                                                                                  | Everything green; real-data checks named in the acceptance pass on staging                                                                                                                                                         |
| BUILD (ship) | `code-reviewer` (Opus) with the **ponytail lens** (anything removable without failing a test is a finding) and its checklist (matches the plan, tests first, boundaries, no secrets or real personal data, errors handled at boundaries, data safety). The agent merges; merge deploys staging; Nimish previews if user-visible                                                                                                                                                                              | PASS + green CI + merged + staging deployed + preview accepted (or not user-visible). Close-out in the same PR: parity row → `done` with evidence, `changes/` fragment, `wiki/log.md` line; the orchestrator rewrites `HANDOFF.md` |

**Stop conditions for a ticket.** Done: as BUILD above. Stop and return the question: plan silent on a file, field or test (determinism rule); three plan or code review FAILs in a row; a test believed wrong (planner, or Nimish if a product rule); a schema change found mid-build; an external input missing (`blocked-external`); the stop hook failing three times (write it into the handoff). A preview "no" becomes a bug ticket (failing test first) in the same milestone.

**One milestone as a persisted goal.** Objective = the gate in §1. Loop: run DEFINE → CODE → TEST → BUILD on the lowest-wave ready ticket per lane until every ticket is merged or dropped with a recorded reason (only M4a-01, M6-00 and a gate no-go may drop or add). Then write `docs/plan/gates/<M>.md` from `_template.md`: gate criteria → tickets → tests → evidence; parity counts; test counts; open product questions; ten steps for Nimish to try on staging; risks; go or no-go. No-go findings become tickets in the same milestone. The next milestone's issues get `ready-for-agent` only after "go". Exceptions: D, S and M1 phase A run together after the H gate; M1 phase B waits for both the D and S gates.
