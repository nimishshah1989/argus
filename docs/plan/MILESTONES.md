# Milestones and tickets — Uptimo

Written 13 November 2026 from `docs/BRIEF.md` (scope and order are binding), `.claude/harness/CLAUDE.md`, `docs/ARCHITECTURE.md`, `docs/DATA-MAP.md`, `docs/decisions/D01–D16`, `docs/plan/ROADMAP.md`, `docs/spec/SPEC.md` §3/§4/§9/§11, `docs/spec/parity.yaml` (80 rows: 16 done, 1 waived, 34 in-progress, 26 todo, 3 external), `docs/plan/NEEDS.md`, `docs/spec/PARITY.md` and the four prototype inventories. It supersedes the ticket lists in `ROADMAP.md` §5 and `backlog.md`.

Rules this plan follows: one ticket = one vertical slice = one GitHub issue = one slice plan = one PR (≤ ~800 changed lines; the slice-planner splits a ticket that exceeds it and says why). Process and doc tickets exist only in H (one exception: M4a-01, the triage the BRIEF prescribes). A design-system ticket precedes every new screen. No ticket depends on M3. Each milestone's schema lands first, as one migration ticket in the schema lane. AI runs in shadow until its threshold; numbers come from code, never from a model. M5 (second plant) is deferred: nothing is planned for it. "Verify" marks a library or extension not yet installed: the slice-planner checks its current documentation before naming any function from it.

## 4. Goal-loop contract

**One ticket as a persisted goal** (the GitHub issue is the goal record; its body carries goal, acceptance, depends, area, lane, wave):

| Step                  | Who                                                                      | Output; passes when                                                                                                                                                                                                                                 |
| --------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 Ready               | Orchestrator (`to-tickets`, H8)                                          | Issue labelled `ready-for-agent`; only the current milestone (one ahead at most). Taken when all `depends on` are merged, its lane is free and its `external` is satisfied; otherwise labelled `blocked-external` and the next ticket is taken      |
| 2 Slice plan          | `slice-planner` (Opus)                                                   | `docs/slices/<issue>.md`: every file, interface, data field, Given/When/Then test that fails first, regression risk, "verify" checks done for any new library                                                                                       |
| 3 Plan review         | `plan-reviewer` (Opus, fresh context)                                    | PASS. A FAIL returns to 2; a product gap becomes a PQ for Nimish, a technical gap is decided by agents                                                                                                                                              |
| 4 Schema/architecture | `architect` (Fable) + `schema-reviewer` / `architecture-reviewer` (Opus) | Only when `schema?` = Y or a contract, module or public route changes. PASS; data-altering migrations carry a backup step and the `approved-by` / `backup:` header (S5)                                                                             |
| 5 Build               | Sonnet, `tdd` + `subagent-driven-development`, on a branch               | Failing tests committed first, then code; whole suite green; no test deleted, skipped or weakened                                                                                                                                                   |
| 6 Code review         | `code-reviewer` (Opus)                                                   | PASS (matches plan, nothing extra, boundaries, no secrets or real personal data, errors at boundaries) and green CI (lint, types, unit, DB, sharded E2E, gallery screenshots, `check-boundaries`, `check-ui`, `check-migrations`, parity, licences) |
| 7 Merge               | The agent                                                                | Merge to `main`; staging deploys (S2)                                                                                                                                                                                                               |
| 8 Preview             | Nimish, if user-visible                                                  | A plain-English note: what changed, what to try on the phone, any product question. A "no" becomes a bug ticket (failing test first) in the same milestone                                                                                          |
| 9 Close-out           | Same PR                                                                  | Parity row → `done` with evidence; `changes/` fragment; `wiki/log.md` line; orchestrator rewrites `HANDOFF.md`                                                                                                                                      |

**Stop conditions for a ticket.** Done: merged, CI green, parity and log updated, preview accepted or not user-visible. Stop and return the question: plan silent on a file, field or test (determinism rule); three plan or code review FAILs in a row; a test believed wrong (planner, or Nimish if a product rule); a schema change found mid-build; an external input missing (`blocked-external`); stop hook failing three times (write it into the handoff).

**One milestone as a persisted goal.** Objective = the gate in §1. Loop: take the lowest-wave ready ticket per lane until every ticket is merged or dropped with a recorded reason (only M4a-01 triage and a gate no-go may drop or add). Then write `docs/plan/gates/<M>.md` from `_template.md`: gate criteria → tickets → tests → evidence; parity counts; test counts; open product questions; ten steps for Nimish to try on staging; risks; go or no-go. No-go findings become tickets in the same milestone. The next milestone's issues get `ready-for-agent` only after "go". Exceptions: D, S and M1 phase A run together after the H gate; M1 phase B waits for both the D and S gates.
