# 0005 — Postgres-backed delayed jobs

Date: 11 November 2026
Status: accepted

## Context

M2 requires delayed SLA timers that survive process restarts and re-arm on every ticket transition.
There is no existing job runner in the repository. SPEC selects pg-boss rather than adding Redis or
another managed queue. Timer and tenant code must share the same database transaction.

## Decision

Use **pg-boss** as the only job queue, in the same Node.js process as Fastify. `ROLE=all` runs API and
jobs; `ROLE=api` disables workers; `ROLE=worker` runs only jobs. The API can therefore split from the
worker later without changing job code.

- Queue names are `sla.timer` and `sla.consistency`.
- Each `sla.timer` job carries `{tenantId, ticketId, kind, revision}` and is re-armed with singleton
  key `{tenantId}:{ticketId}:{kind}` using pg-boss `upsert`, not ad-hoc polling or decrement-only counters.
  Cancellation finds jobs by key and cancels only the previous revision's ids.
- Job writes use the pg-boss DB adapter (`executeSql`) over the ticket's `PoolClient`, so ticket,
  timer and queue writes commit or roll back together.
- Handlers re-read the ticket/timer inside `withTenant` and use an atomic conditional UPDATE guarded
  by id, revision, current dueAt and `fired_at IS NULL`. Terminal/already-fired work is a no-op;
  a stale revision never fires merely because it was queued.
- A startup/daily consistency job re-arms missing or stale timers. Cross-tenant discovery returns only
  tenant ids through a narrow `app_router` security-definer function, then each tenant is processed in
  its own RLS transaction.
- pg-boss's own schema is a documented exception to the tenant-table RLS rule. Tenant payloads never
  include secrets. A privileged migration installs the schema once; runtime uses `migrate:false`
  with `app_user` limited to queue table access.

API references: [pg-boss jobs and upsert](https://pgboss.io/api/jobs) and
[pg-boss README](https://raw.githubusercontent.com/timgit/pg-boss/master/README.md).

## Why not the alternatives

- **Redis / another managed queue:** another state store and cost with no benefit at this scale.
- **An in-memory `setTimeout`:** loses timers on restart and cannot make ticket+timer commits atomic.
- **A custom polling queue:** duplicates SKIP LOCKED, retries, scheduling and dead-letter behavior that
  pg-boss already provides under MIT.

## Consequences

`pg-boss` becomes a new runtime dependency and must be pinned and included in `THIRD_PARTY.md` and the
licence check. Tests use a real disposable Postgres, short polling intervals and direct queue/worker
invocation rather than wall-clock sleeps. Business rules remain pure functions in `packages/domain`.
