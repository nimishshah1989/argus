# Review 03 — Can Claude Code build this autonomously?

Reviewer lens: an AI coding agent working the goal loop alone, with Nimish appearing only at milestone gates. Domain edge cases and over-complexity are covered by the other two reviewers and are left out here.

Documents read: `spec/SPEC.md` (all 13 sections), the two Claude Docs tabs "Domain model & API" (DOMAIN) and "Parity checklist" (PARITY) exported to markdown, `02-KICKOFF-PROMPT.md`, `README.md`, `bhavin-v3/INVENTORY.md`, `live-config-2026-11-09.json`, `glossary-2026-11-09.json`, and the folder listing of the pack (`atlas-poc/`, `research/`, `prototype-inventory/`, `source/`).

## Verdict

1. **Partially.** The domain core (schema v1, RLS, auth, state machine, figures, tickets API, floor and desk screens, follow-up tasks, PDFs) is specified well enough for an agent to build M0 0.1–0.6 and M1 1.1–1.7 and 1.9 with gate-only review; DOMAIN is the strongest document in the pack and INVENTORY is specific enough to port from (line-referenced copy, payloads, rules).
2. **Not as written** for M0 0.7 (needs AWS, domain, GitHub secrets from Nimish), M1 1.8 (physical devices), 1.10–1.11 and M2 2.6 (Bhavin's data, a human week, a human decision): these have no fallback rule, so an autonomous agent either stalls or invents.
3. **The single biggest gap is operational, not technical:** the loop ends every ticket with "open a pull request" and then "pick the next ticket", but nothing says who merges, how the next branch is based, which of three deploy triggers puts the change on staging, or how the next session learns where the last one stopped. After PR #1 the agent is guessing. (Nimish's saved preference, from memory, is that Claude merges green PRs itself; the kickoff and SPEC §10 instead imply he reviews on staging first.)
4. **Two of the three spec files the kickoff orders the agent to read first (`DOMAIN.md`, `PARITY.md`) are not in the pack**; only `SPEC.md` is in `spec/`. Trivial to fix, fatal if forgotten.
5. There is one real design contradiction an agent cannot resolve alone before writing migration 0001: "tenant never from the URL or a header" versus a login request with no tenant, usernames unique only per tenant, fixed `/floor` routes, `GET /brand?tenant=slug`, and RLS that needs `app.tenant_id` set before the `login` row can be read.

## Notes on the parity material

## Goal-loop assessment against the six questions

- Know what to do next: yes, via backlog.md, provided the merge and continuation protocol (finding 2) and the blocked-external rule (finding 3) exist.
- Know when done: per-ticket DoD is clear except "deployed to staging" (finding 2) and the manual criteria (finding 19).
- Record decisions without blocking: QUESTIONS.md and DIFFERENCES.md are good; the "data or money" threshold needs a definition (finding 24).
- Avoid drifting from parity: parity.yaml exists only in name (finding 9).
- Stop at the right moments: gates are defined but the gate report is not (finding 10); there is no stop for cost, destructive migration, or production (finding 20).
- Safety rails: rule 11 is good intent without mechanism (findings 16, 20, 21, 28).
