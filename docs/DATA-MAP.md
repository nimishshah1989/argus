# Data map — Uptimo

For Nimish. This is everything the product stores, in plain words: what each thing is, how the things connect, who can see or change them, and which of them is personal data. You approve this document; the questions at the end are the ones only you can answer.

Written 13 November 2026 from `docs/BRIEF.md`, the spec, and the database as it exists today (changes 0001 to 0007). The technical name is in brackets so the reviewers can match each line to the database. "Owner" is the part of the server that is allowed to write that thing (see `docs/ARCHITECTURE.md`, Part 2).

## 1. The picture in one page

- A **customer** (today only Cosmos) is one plant. Everything below belongs to exactly one customer, and the database itself refuses to show one customer's rows to another.
- A plant has **people** and **logins**. A person is a human being (a technician, an operator, a vendor's engineer). A login is a username and password; it is either personal (tied to one person) or a shared phone on the floor. On a shared phone, each action also records which person did it.
- A plant has **machines**, sorted into segments, groups and cells, and a set of **lists and settings** that make it this plant and no other (wait reasons, work types, shifts, targets, wording).
- A **ticket** is one breakdown or one work request. Everything that happens to it is written as a line in its **history**, in order, and never edited afterwards. The history is the truth; the numbers on the ticket (response time, downtime, hands-on time) are worked out from it.
- When work happens, the ticket records **who was on the job** and **each stretch of time each person worked**. When it is closed, a **breakdown report** is filled in and a PDF is made.
- From M2, each ticket has **two clocks** (acknowledge and restore), a **ladder** of who is told when a clock is missed, a **duty roster** saying who is on that ladder today, and a **sign-off** by production.
- From M4, the old breakdown history and the live tickets feed the **analytics engine**, which stores its results (KPIs, forecasts, the monthly scorecard). **Preventive maintenance** plans create scheduled tasks. Each closed breakdown gets **failure codes**.
- From M6, the **AI** stores its suggestions and whether a person accepted them. A suggestion changes nothing until a person confirms it.
- Last, in M3, **WhatsApp** contacts, conversations, messages and voice notes.

## 3. How the things connect

- Customer → people, logins, machines, lists, settings, tickets. Nothing is shared between customers.
- Login → at most one person. A shared login has no person of its own.
- Machine → one segment, one group, one cell at a time; its moves are dated.
- Ticket → at most one machine (none for general work), many history lines, many crew members, many work stretches, at most one breakdown report, any number of follow-up tasks (each a small ticket pointing back to its parent).
- Ticket → its clocks, its escalation records, its sign-off (M2); its failure coding (M4b); its AI suggestions (M6); its WhatsApp conversation (M3).
- Machine → PM plans → tickets raised with channel `pm` → that ticket's report data (`pm_report`) (M4b). Machine → figures and forecasts (M4).
- Person appears on tickets, history, crew, work stretches, reports, roster, notifications. This is why a person is switched off rather than deleted.

## 5. Personal data and the law (DPDP Act 2023)

What we hold about people is small and work-related: name, job title, team, shift, optionally a mobile number, a username, what they did on tickets and when, and later their voice and WhatsApp messages. No home address, no date of birth, no ID numbers, no health data, no data about children. It stays that way.

- **Only what is needed.** A mobile number is optional and is needed only for WhatsApp (M3). Operators who only use a shared phone need no login and no number, only a name on the pick-list.
- **Purpose.** Data is used to run and improve maintenance at that plant. Any other use needs the customer's agreement (question 7).
- **Location.** Everything is stored in AWS Mumbai. Nothing leaves India unless a written decision with a data-protection note says so (BRIEF). Push notifications pass through Google's and Apple's services, as with any app; their content is kept to the ticket number and machine, with no names.
- **Consent.** A consent message on first WhatsApp contact; voice notes only from people who agreed (need N6, N14).
- **Our role.** The plant decides what is collected; we process it for them under a short agreement.
- **Deletion and correction.** A person can be corrected or switched off at any time. Full removal has to reach every place a name can sit, including free text; the table below lists them. The level was decided on 13 November (question 1).
- **No real data in the code.** Tests and screenshots use made-up names. Real Cosmos data on the staging site needs your answer to question 3.
- **Logs** carry ids, never names, numbers or message text.

## 6. Changes to data that already exists

**What has already happened.** Nothing is live, so no real plant data has been changed. Two earlier database changes did rewrite stored rows on test data, and both are recorded here as dated exceptions to our own rules:

- Change 0006 filled in a severity on older tickets from the machine's importance at the time of the change. It was labelled as adding only. It cannot be undone exactly, because a filled-in value looks the same as one set when the ticket was raised.
- Change 0007 added a "paused the clock" mark to older pause lines in ticket history, which is meant never to be edited. It asked for a backup first and changed no times or figures.

**What this plan changes.** New things are new tables beside the old ones. A small number of existing things do change, grouped into one reviewed database change per milestone (the list, by milestone, is at the top of `docs/ARCHITECTURE.md` Part 9): tickets, their history, crew, work stretches and reports become impossible to delete from the app, and history impossible to edit; people, logins and list entries are switched off, never deleted; machines and stored files cannot be deleted from the app either (today the app does delete list entries, which is a fault); one open breakdown per machine becomes a database rule (a check run before the change lists any duplicates; the change does not start until a person resolves them, and nothing is fixed automatically); tags are removed (decided); the duplicate team field on a person, and two unused fields on a ticket, stop being used and are removed later; clean-up of old sign-ins and repeat-guard notes begins.

**The rule for every change that touches stored data**

1. **Backup first.** A full database snapshot is taken and its reference written into the change itself before it runs. On staging first, always.
2. **Add, then switch, then remove.** A change first adds the new shape alongside the old, the app is released using the new shape, and only a later release removes the old one.
3. **Leave a trace.** A change that fills in or rewrites values records each row's old and new value in the audit trail under the change's name, so it can be told apart and reversed. The two changes above did not.
4. **Roll back.** Because the old shape is still there, going back is re-releasing the previous version. If data was changed wrongly, the old values from step 3 are put back, or the snapshot from step 1 is restored; the restore is rehearsed before cutover and every quarter.
5. **Checked.** The schema reviewer must pass it. The automatic check is weak today: it only looks at the start of a line, so even a removed column can slip past, and it does not see rewrites or tightened rules. Fixing it, and making it demand the reviewer's approval mark and the backup reference, is due before cutover and before any removal in this plan.
